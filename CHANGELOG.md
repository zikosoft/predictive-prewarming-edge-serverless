### 1. Direct forecast-quality metrics (Family C) — answers RQ3 from forecast error directly, not just downstream latency

**Added:** `analysis/analyze_v5_forecast_quality.py`. Each predictor's forecast error is reconstructed from the already-collected primary N=15 raw per-request timestamps (not a new measurement or simulation): the exact sequence of inter-burst silences each predictor observed is recovered by replaying its deterministic update rule (Section 2.5) over the same gap sequence the live gateway logic used. **Result:** mean absolute error and signed bias computed per predictor; a sixth paired-Wilcoxon-plus-Holm-6 family (Family C, same design as Family B/RQ3) run on trial-level MAE finds no statistically significant pairwise forecast-error difference among any of the four predictors (Holm-adjusted p from 0.062 to 1.000). ## v4 — Round-2 methodological reanalysis (statistical design correction + two new pilot experiments)

A second, deeper pre-submission methodological pass (after v3/v3.1's bug fixes) found that the *statistical design* used to test the primary result — not the measurement code — had two flaws, and flagged five further rigor gaps. No measurement code changed in this pass; every item below is either a reanalysis of already-collected raw data with corrected statistics, or a new pilot experiment that reuses the existing, unmodified measurement path (`loadgen/orchestrate_and_run.py`'s `run_policy_scenario_independent`) under new environment-variable conditions.

### 1. Merged correction family answered only H4, never RQ3 (critical)

**Problem:** the v3 analysis Holm-corrected a single 4-test family (each predictor vs. reactive) and reported it as answering both "does each predictor beat reactive" (H4) and "do the predictors differ from each other" (RQ3) — but a single family built around one baseline can only ever answer the first question.

**Fix:** `analysis/analyze_v4_corrected.py` (new) splits this into two independently Holm-corrected families: Family A (H4, 4 tests, each predictor vs. reactive) and Family B (RQ3, 6 tests, every predictor-pair). Run on `results/trial_level_table.csv`, cyclical scenario, N=15 matched trials, paired Wilcoxon signed-rank per contrast.

**Result:** under Family A, all four predictors are significant against reactive after Holm-4 correction (Holm-adjusted p = 0.036 EWMA, 0.020 last-gap, 0.036 moving-average, 0.0002 fixed-schedule) — reversing the previous "only two of four survive correction" conclusion, which had come from an unpaired Mann-Whitney test on a merged family. Under Family B, the three adaptive forecasters are statistically indistinguishable from each other (all Holm-adjusted p=1.000); fixed-schedule is significantly faster than all three (Holm-adjusted p≈0.0004 each).

### 2. Hodges-Lehmann estimator mislabeled (critical)

**Problem:** the v3 revision reported the *median of the paired differences* as if it were the Hodges-Lehmann estimator. The correct paired-sample HL estimator is the median of the `n(n+1)/2` pairwise Walsh averages `(d_i + d_j)/2` of the paired differences — a related but numerically different quantity.

**Fix:** `analysis/analyze_v4_corrected.py`'s `hodges_lehmann_walsh()` implements the Walsh-average definition directly, plus a distribution-free 95% CI from the Walsh-average order statistics and the matched-pairs rank-biserial correlation from the signed-rank sums (Kerby 2014) rather than an unpaired Mann-Whitney-derived rank-biserial. Both the median difference and the correct HL estimate are now reported side by side, correctly labeled, in `results/v4_family_A_H4_vs_reactive.csv` and `results/v4_family_B_RQ3_pairwise.csv`.

### 3. "Comparable" opportunity-conversion claim was never statistically tested

**Fix:** `analysis/analyze_v4b_opportunity.py` (new) computes per-trial opportunity-conversion rate for all four predictors from already-logged `results/gateway_stats.csv` counts (structural opportunity denominator: 4/trial for fixed-schedule, 3/trial for the three adaptive forecasters — verified as an exact constant, `gap_observations`=4.0, std=0, across all 60 predictor-trials) and tests it with the same paired-Wilcoxon+Holm-6 design as RQ3. Result: 5 of 6 pairs are not significantly different; last-gap's conversion rate is significantly lower than fixed-schedule's (Holm-adjusted p=0.040).

### 4. Fixed-schedule period sensitivity sweep and non-oracle keep-alive baseline (new pilot experiments)

**Added:** `loadgen/orchestrate_round2_sweeps.py` (new), a thin orchestration layer that reuses `run_policy_scenario_independent` unchanged, monkey-patching only `FIXED_PREDICTED_GAP_S` (sweep: -50/-25/-10/+10/+25/+50% of the disclosed nominal 9.0s) or `IDLE_TIMEOUT_S` (sweep: 8/10/12s, vs. the primary run's 6.0s reactive baseline) per run. N=6 independent trials per new condition (pilot scale; the primary N=15 protocol's nominal points are reused rather than re-run). Output under `results/raw_fixedsweep/*/`, `results/raw_keepalivesweep/*/`, and `results/fixedsweep_*.csv` / `results/keepalivesweep_*.csv`. Analyzed by `analysis/analyze_v4d_sweeps.py` (new).

**Result (fixed-schedule):** the latency advantage is flat under every under-estimate tested (-50% to -10%) and collapses sharply and asymmetrically under over-estimate — at +10% the opportunity-success rate is still 79% yet mean-of-trial-median latency has already jumped 3.3x; at +50% fixed-schedule is slightly worse than plain reactive scaling. **Result (keep-alive):** no benefit at 8.0s (the workload's own minimum idle gap); a sharp step-function improvement at 10.0s/12.0s (at/above the workload's own maximum idle gap) — cold-start rate 20%→4%, latency ~12x lower — showing a non-oracle, round timeout choice at the workload's disclosed upper bound already captures effectively all of an oracle-tuned choice's benefit.

Tagging resource rows with their sweep condition is a small fix recommended before any full N=15 confirmatory run.

## v3.1 — second, deeper bug found only after v3's fix (prewarm trigger reference-frame mismatch)

Fixing the v3 contamination bug (below) was itself what exposed this one: once the forecast was no longer collapsing to near-zero, `results/gateway_stats.csv` showed `predictive_cold_starts = 0.0` across **all 15 cyclical trials** for the `ewma`, `lastgap`, and `movavg` predictors — despite `predicted_gap_s` correctly converging to ~9-10s, matching the true simulated inter-burst silence. Only the `fixed` predictor ever fired (about once per trial in 14/15 trials). A predictor that (correctly) forecasts the gap but (almost) never gets to act on that forecast cannot demonstrate anything, so this was found and fixed before any manuscript numbers were finalized.

**Root cause:** `gateway/elastic_gateway.py`'s `predictive_prewarmer()` measured its idle-time clock (`idle_elapsed`) from `empty_since` — the moment the instance pool became fully empty — and compared it against a threshold (`predicted_gap_s - STARTUP_LEAD_S`) calibrated against the *full* inter-arrival gap, measured from the last genuine request. These are not the same clock: the pool can sit non-empty for up to `IDLE_TIMEOUT_S` (6s) *after* the last real request, because the reaper only retires an idle instance after that timeout. So of the true ~9-10s silence between bursts, only the last ~3-4s (`gap - IDLE_TIMEOUT_S`) was ever counted as "idle" by the trigger — far short of the ~8-9s (`predicted - STARTUP_LEAD_S`) needed to fire. The trigger was, for any predictor with an accurate forecast, comparing a truncated clock against a threshold sized for the untruncated one. (`fixed`'s flat, always-available threshold happened to be reachable anyway from the first cycle, which is why it alone appeared to "work" and is also why its apparent behavior in v3-pre-fix data cannot be trusted as representative of the predictor's actual quality — it was firing on volume, not on being well-calibrated.) This bug predates v3; it was present identically in v2, but its effect was masked there by bug #1 (contamination): a collapsed near-zero forecast makes `predicted - STARTUP_LEAD_S` trivially small, so the (wrongly-referenced) trigger fired almost immediately regardless — two bugs cancelling into a coincidentally-plausible-looking result.

**Fix:** `idle_elapsed` is now measured from `_last_real_arrival["t"]` (the same genuine-external-arrival timestamp the predictor's own forecast is calibrated against — see bug #1's fix below), not from `empty_since`. A `already_prewarmed_for_this_idle_period` flag replaces the old `empty_since` bookkeeping, so the prewarmer attempts at most one anticipatory spawn per idle period rather than re-evaluating every 100ms poll tick once past threshold.

**Verified:** a smoke test (4 compressed ~9.5s-gap cycles) went from 0/4 to 2/4 predictive fires. The full corrected re-run (`loadgen/rerun_predictive_fix.py`, cyclical scenario, all four predictive policies, 15 independent trials each, learning-curve run for reactive+EWMA) shows `predictive_cold_starts` averaging 2.4-4.0 per trial across all four predictors — a real, non-degenerate signal for the analysis to work with. Only the cyclical scenario's four predictive policies (and the ewma+reactive learning-curve run) needed re-running: container, reactive, and the low/moderate scenarios never call `predictive_prewarmer()` or don't have idle gaps long enough to exercise it, so that data was reused unchanged (see `loadgen/rerun_predictive_fix.py`'s docstring for the exact scope argument).

## v3 — corrected after external methodological review

An external review of the v2 draft manuscript and code identified five issues before submission. All five were verified directly against the code and data (not taken on faith) and fixed. This entry documents each, for transparency and because it is itself part of the paper's reproducibility record.

### 1. EWMA gap-tracker contamination (critical)

**Symptom found in `results/gateway_stats.csv` (v2 data):** the predictive policy's forecast (`ewma_gap_s`) collapsed over successive trials — 3.43s → 1.64s → 0.326s → 0.171s → 0.158s — while the true simulated inter-burst idle period was 8-10s.

**Root cause:** `gateway/elastic_gateway.py`'s `gap_tracker()` inferred "a new burst has started" from the pool's dict transitioning from empty to non-empty. But `_reserve_slot()` inserts a placeholder into that same dict the instant the *predictive prewarmer* reserves a slot for its own speculative spawn — before any real request has arrived. A successful anticipatory prewarm was therefore indistinguishable, to the gap tracker, from a genuine burst arrival, and got recorded as a very short "observed gap." This fed back into the EWMA, which chased its own trigger threshold downward every cycle.

**Fix:** gaps are now recorded exclusively in `_note_real_arrival()`, called only from `handle_invoke` (the gateway's external HTTP entry point) — never from the prewarmer. The prewarmer's own pool mutations are structurally invisible to the gap-observation logic. Verified by direct testing: the forecast now converges to and stays near the true simulated gap across repeated cycles instead of collapsing (see commit history for the smoke-test output).

### 2. Asymmetric measurement path

**Symptom:** the container architecture's load was sent directly from the load generator to each replica (`.../ingest`, zero hops); both serverless architectures were sent through `elastic_gateway.py`'s `/invoke` (one extra local HTTP hop plus `asyncio` lock bookkeeping). This was measurable even in the no-cold-start "low"/"moderate" scenarios (container p50 ≈ 1.7ms vs. reactive/predictive p50 ≈ 2.85ms).

**Fix:** added `gateway/container_gateway.py`, a same-shape one-hop proxy fronting the persistent replicas, emitting the identical response-header instrumentation as `elastic_gateway.py`. The container architecture is now measured through the same kind of path as the others; only the deployment/scaling policy differs.

### 3. Pseudoreplication in the statistical tests

**Symptom:** `analysis/analyze.py` (v2) pooled every individual request across all 5 trials of a (scenario, architecture) pair into one array and ran Kruskal-Wallis / Mann-Whitney treating each request as an independent observation, despite (a) requests within a burst being correlated by shared queueing state and (b) the predictive policy's trials deliberately sharing persistent EWMA state.

**Fix:** `loadgen/orchestrate_and_run.py` now restarts the backend fresh before every trial (no state carries over between trials), and trials for a given (scenario, trial-index) share an RNG seed across *all* policies (matched design). `analysis/analyze.py` computes trial-level median latency first and runs all significance tests on those N=5 (short scenarios) or N=15 (cyclical) trial-level values, plus a paired Wilcoxon signed-rank test exploiting the matched seeds. The learning-curve behavior (predictor improving with repeated exposure) is now a separate, explicitly-labeled, descriptive-only run (`results/raw_learning/`) rather than being conflated with the hypothesis test.

### 4. No baseline ablation for the predictor

**Symptom:** only the EWMA policy was implemented and compared to a non-predictive reactive baseline, so the manuscript could not show how much of the improvement was attributable to EWMA specifically versus any prewarming heuristic at all.

**Fix:** `gateway/elastic_gateway.py`'s `GapPredictor` is now pluggable (`PREDICTOR=ewma|lastgap|movavg|fixed`); `analysis/analyze.py` produces `baseline_comparison_table.csv` comparing all four against the reactive baseline and the container architecture on identical, seed-matched cyclical-scenario traffic.

### 5. Repository/manuscript drift

**Symptom:** the README described two architectures instead of six policies, referenced a deleted file (`gateway/faas_gateway.py`), documented a workload scenario ("burst") that no longer existed, and falsely stated the manuscript had been submitted.

**Fix:** README rewritten to match the current repository exactly (this file's existence is part of that fix). `CITATION.cff` and `.zenodo.json` added. The repository is deliberately **not yet archived to Zenodo** — see README, "Data availability & citation."
